  2. The stack

  - Daml: the smart-contract language, derived from Haskell. Packages are DAR
    files, built with the DPM command-line tool.
  - Canton: the protocol and node software, written in Scala. Validator nodes
    host parties; synchronizers order transactions. Privacy is per
    sub-transaction, so nodes only see what their parties are involved in.
  - Splice: the network apps (Canton Coin, validator and super-validator apps,
    the Scan public API, wallet, name service). Scala backend, TypeScript/React
    frontends, deployed with Helm/Kubernetes.
  - Integration layer:
    - Ledger API over gRPC or JSON, with JWT/OAuth authentication.
    - PQS, which streams ledger data into Postgres.
    - Wallet SDK, dApp SDK and Wallet Gateway.
    - CIP-56 token standard.
    - SDKs in Java, TypeScript, Go, C#, Rust and Python.
    - LocalNet (cn-quickstart) for local development.

● Yes. An RFP-aligned proposal still needs a Champion if you're an external
  team, which you are. The repo puts it this way:

  - README.md: "External contributors must have a Champion to support the
    proposal." This applies to both RFP proposals and individual initiatives.
  - rfps/README.md: the checklist for RFP proposals includes "5. Identify a
    Development Fund Champion."
  - PR template: every submission has to name a Champion or tick Needs Champion.

  What I missed before is who can be a Champion. sig-directory.md says: "Under 
  CIP-0100, an external Development Fund proposal requires a Champion from the 
  Tech & Ops Committee. SIG membership alone does not give an individual or 
  organization formal Champion status." So a friendly SIG member isn't enough;
  you need someone on the Tech & Ops Committee.

  What this means for you:
  - You can open the PR with Needs Champion. Reviewers can also tag it that way
    if it looks promising but needs work.
  - The Champion is the person who moves it to "Ready for Vote". In practice,
    without one the proposal sits in the queue.
  - Foundation members and contributor organisations such as Digital Asset don't
    need one, which is part of why their proposals move faster.
  - The labels on the open PRs don't tell you much. Of 102 RFP-tagged open
    proposals, only 9 are labelled champion-confirmed and 2 needs-champion; the
    rest aren't labelled either way. Read the PR body to see who the Champion
    is.

  So finding a Tech & Ops Committee member to back you belongs in the RFP
  decision itself, not as a step after it. I've added this to CLAUDE.md.

  How it's built
  - Test scenarios are written once, in a language-neutral format (YAML).
  - A Python test runner sends each step to a small adapter per SDK, which runs
    it against a local Canton network and reports the result. Adding an SDK
    means writing one adapter; the runner doesn't change.
  - A test Daml package covers every data type, plus one interface, a contract
    key, and choices that succeed and fail.
  - SDKs first: Digital Asset's TypeScript SDK, dazl (Python), Nodejumper's Rust
    SDK, and our own plain-HTTP reference adapter, which serves as the baseline
    when results differ.
  - Results feed a public compatibility table, pinned to one Canton version.

  Scenarios most likely to turn up real differences
  - Data-type round-trip: decimal precision, timestamps, maps, nested optional
    values.
  - Errors: whether each SDK marks an error as retriable, and how it reports it.
  - Externally signed transactions: checking that each SDK computes the same
    transaction hash as FTP's funded hashing library.
  - Token transfers: a Canton Coin transfer using the CIP-56 token standard.
  - Recovery: resuming a dropped event stream, and recovering a command after a
    crash.

  Schedule
  - Week 1: the core scenarios run against 3 SDKs, then a check that each
    difference is a real bug and not our misunderstanding.
  - Week 2: signing, token transfer, recovery, upstream issues, a one-page
    write-up and a 3-minute video.
  - Success: at least 3 confirmed differences filed upstream. If the SDKs all
    agree, the pitch shifts to keeping them in sync across Canton releases.

  - The local Canton network is heavy. GitHub's hosted CI machines will probably
    be too small, so expect a self-hosted or AWS runner, which is a natural job
